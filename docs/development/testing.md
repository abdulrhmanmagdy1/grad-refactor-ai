# Testing and verification

## Foundation checks

The tests cover health reporting, blank and oversized input, invalid syntax, long async functions, and structural nesting. A submitted example containing a file-write operation verifies that analysis does not execute that example. Dataset-validator tests cover empty or missing splits, source-group overlap, and normalized duplicates.

These tests verify the foundation. They do not establish model quality, complete refactoring behavior, or runner isolation.

## First-release test plan

- Unit tests for role schemas, transformations, and tools.
- Integration tests for run transitions, model failures, timeouts, and bounded retries.
- Acceptance tests traced to the agreed requirements.
- Regression examples with checked reference tests.
- Runner checks for resource limits, isolation, process cleanup, and absence of network, secrets, and host access.
- A clean installation and full demonstration in a fresh environment before delivery, preferably on a second physical machine; record the actual hardware coverage.

Tests generated by the same model are not sufficient evidence for its own changes. Combine reference tests with a declared assessment rubric. Passing tests does not prove complete semantic equivalence.

## Continuous integration

GitHub Actions runs lint, format, pytest, and local Markdown-link checks on Linux and Windows using the locked core environment. It does not train models, download weights, or execute user-submitted code. Monitor the free Actions allowance; paid overages are not part of the plan.
