# إعداد بيانات Refactoring

## المنفذ الآن (P5)

`data/curated.jsonl` يحتوي **416 سجلًا** مؤلَّفًا/مصنَّعًا داخل المشروع (لا scraped): 8 أنواع
Refactoring × 52 سجلًا لكل نوع (28 سجل findings + 24 سجل clean-control). الحقول: `id`
و`source_group` و`split` و`prompt` و`completion` و`license` و`refactoring_type` و`smell_rule`
و`variant` و`template_style` و`verification`. الأنواع الثمانية: long-function، deep-nesting،
high-complexity، async-function، mutable-default-arg، duplicate-code، long-parameter-list،
broad-exception.

التقسيم: train 320 / validation 48 / test 48. لكل نوع:
train 20 findings + 20 clean-control، validation 4 findings + 2 clean-control، وtest 4 findings
+ 2 clean-control. هذا يجعل التدريب 50/50 بين وجود findings وغيابها، ويعطي اختبارًا صريحًا
لقدرة النموذج على عدم إعادة كتابة كود نظيف. التمييز حسب `source_group` =
`authored-<type>-<split>` أو `authored-<type>-clean-<split>`؛ البيانات مؤلفة فلا تسرب خارجي.

كل سجل findings تحقق آليًا قبل الكتابة عبر `scripts/generate_curated_dataset.py`:

- الـprompt يجب أن يُفعّل قاعدة الكشف المعلنة (`smell_rule`) عند تحليله بـAST، وأن يكون صالح
  الـsyntax، ومكتوبًا بهوية identifier فريدة لكل سجل.
- الـcompletion يجب ألا يُفعّل القاعدة نفسها بعد التعديل، وأن ينجح في تحقق آلي فعلي:
  إما `golden-equivalence` (اختبارات ذهبية مولدة من مولّد التكافؤ تُنفَّذ في Runner المعزول
  على عينات مدخلة ثابتة وتقارن مخرجات الأصل والمرشح)، أو `authored-smoke-test` للأنواع
  المتغيرة التوقيع بطبيعتها (long-parameter-list) حيث لا تصلح مقارنة الاستدعاء المباشر —
  وهذا مسجل صراحة في السجل ولا يُخفى.
- سجلات `clean-control` هي أزواج identity: الـprompt هو نفسه الـcompletion، ويتحقق المولّد
  بـAST أن الـprompt لا يحمل أي finding. لا يُنفَّذ كود فيها لأن لا تغيير سلوكي للمقارنة؛
  الطريقة مسجلة باسم `clean-control` في المانيفست.
- كل نوع لهقالب 2–3 أشكال بنيوية (`template_style`)، مع identifiers وثوابت مختلفة لكل variant.
- لا تحمل الـprompts أي تعليق `# example:`؛ يجب أن يرى التدريب نفس الكود الذي يراه الاستدلال.
  المصدر موثق في `id` و`source_group` والمانيفست.

الترخيص: CC0-1.0 (محتوى مؤلف داخل الفريق، بلا نسخ من مصادر خارجية). `data/manifest.json`
يحمل sha256 للملف وعدّادات الأنواع والتقسيمات وfindings/clean و`template_styles` وأساليب
التحقق، ويُحدَّث تلقائيًا عند التوليد.
بوابة القبول: `uv run python scripts/validate_dataset.py data/curated.jsonl` — تتحقق من
الحقول والتقسيمات والتكرار النصي وتعشيش `source_group`. ويُفحص طول كل سجل مقابل نافذة
التدريب عبر `uv run python scripts/audit_tokens.py data/curated.jsonl --max-length 2048`
(الوضع الافتراضي proxy بلا tokenizer؛ مرّر `--tokenizer` للحصول على عدّ دقيق).

## وحدة البيانات (المستهدف الممتد)

سجل يحتوي `id` و`source_group` و`split` و`prompt` و`completion` و`license` و`refactoring_type`.
الـprompt يصف المهمة والكود الأصلي، والـcompletion هو الناتج المرجعي الذي راجعه التيم. تحفظ
معلومات المصدر والـcommit والاختبارات المرجعية في manifest مرافق. أي توسعة مستقبلية بمصادر
خارجية تلتزم بالسياسة التالية.

## الجمع والتنظيف (للمصادر الخارجية مستقبلًا)

نختار مصادر مرخصة ومتوافقة مع تدريب وتوزيع المخرجات المطلوبة. نسجل الترخيص لكل مصدر ولا نفترض
أن كل كود على GitHub مباح للتدريب. نراجع صحة Python قبل وبعد، ونستبعد تغيير الوظائف أو الأمثلة
الغامضة والأسرار والبيانات الشخصية. يمكن بناء أمثلة تعليمية يدويًا أو بتحويلات محدودة
ومراجعتها؛ صحتها وتنوعها أهم من العدد — وهو النهج المطبق فعليًا في المجموعة الحالية.

## التقسيم ومنع التسرب

تقسيم 80/10/10 حسب `source_group` لا حسب الصفوف عشوائيًا؛ المجموعة الحالية مؤلفة فالتسرب
الخارجي منعدم، ويبقى فحص التكرار النصي والتعشيش ضمن التقسيمات. نستخدم validation لضبط
الإعدادات، ونجمّد test قبل الاختيار النهائي. نحفظ hash للملف وmanifest للإصدارات. لا نخلط
أمثلة الاختبار في prompts أو أمثلة التوثيق المستخدمة لضبط الموديل.

## قبول البيانات

مصدر وترخيص واضحان، مراجعة عينة موثقة، حقول مكتملة، كود مرجعي صالح، فصل حسب المصدر، سجل حذف
وتكرار، واختبارات مرجعية للمهام التي نقيس الحفاظ على سلوكها — كلها متحققة للمجموعة الحالية
باستثناء المراجعة البشرية المستقلة التي تبقى مطلوبة قبل الاختبار النهائي.
