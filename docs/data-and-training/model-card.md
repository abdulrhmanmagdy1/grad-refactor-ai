# Model card

**Status: trained and adopted for the refactoring role on validation data.** A LoRA adapter for the refactoring role was trained on the curated train split on 2026-10-21. The rule written before any comparison ([validation-selection-2026-10-20.json](../../experiments/training/validation-selection-2026-10-20.json)) adopts it when arm C has more `proposal_ready` cases than arm A on the full validation split; arm C had 69 of 84 and arm A 6 of 84, so the service uses the adapter for the refactoring role, while analysis and review keep the base model. On the frozen test split (protocol eval-v1, 88 cases) the adapter with one role was accepted in 70 cases against 7 for the base model ([test results](../../experiments/evaluation/test-2026-10-21/targets-report/summary.md)); the supervisor has not reviewed the choice.

Measured context facts: the refactoring prompt adds about 141 tokens to the code, a realistic 3,000-character function is about 770 tokens, the longest curated record is 695 tokens, and inputs dense in digits or non-ASCII text can reach one token per UTF-8 byte. Observed failure cases: on validation, rewrites that keep the guard-clause shape but change behavior (15 of 84 for arm C, in five template families) and a base-model answer cut off inside its code block; on pilot material, an output that dropped a branch of the original function, outputs that kept the nesting, and explanations that stated nesting depths the model did not check. The intended use requires human review and does not guarantee behavioral preservation.
